# 路线选择建议（2026-09-18）

> 问题：下一步朝哪个方向走——①死磕优化追平 torch ②疯狂融入新算法（QSA/DSA/GDN/Mamba-2/RNN/CNN/LSTM）
> ③全面完善引擎设计、简化代码量？
>
> **已确认前提（2026-09-18）：目标 = 学习/作品集（展示架构设计能力）；主战场 = GPU/Vulkan。**
> **最终建议见 §5。**（§1–§4 是按"性能是目标"推导的过程分析，保留作为对照；前提改变后排序随之改变。）

---

## 1. 关键判断：现状里只有一个"一处修复、三处受益"的点

本次诊断（`11-cpu-performance-diagnosis.md`）测出的事实：

| 路径 | 实测 | 判定 |
|------|------|------|
| blocked matmul（CPU） | 162 GFLOPS / 14.7 核 | ✅ 可用 |
| LayerNorm / RMSNorm / Softmax | **0.94–1.00 核**，42/27/41 ms（393K 元素） | ❌ 完全串行 |
| MHA / Transformer / GPTBlock | **2.3–2.8 / 32 核**，8.5 GFLOPS | ❌ 83% 时间在串行 DSL |
| 参考 LayerNorm 实现 | 串行 4.67ms → 16 线程 0.55ms | **相对现状 ~77x** |

这不是"kernel 写得不够好"，而是**架构性退化**：`dsl::compute` 在 CPU 上退化成
**单线程逐元素解释器**（`eval_cpu` 串行 + `eval_expr_impl` 单线程解释，见 §8 设计溯源）。

**为什么说它一处三受益**：

- 对 **① 性能**：这是当前最大的性能漏洞，且边界清晰（不是无上限的 kernel 微调）。
- 对 **③ 引擎**：修它必须把现在并存的**四套求值机制**（旧代数 AST / `eval_cpu` / 解释器 / GPU AOT）
  收敛成一条 lowering，正好是"简化"的实质内容——而不是为简化而简化。
- 对 **② 新算法**：新算法加进来就得有统一的执行面；现在每加一个层要同时应付四套机制。

---

## 2. 逐项评估

### 2.1 ① 死磕优化追平 torch

**作为绝对目标：不建议。** 理由：

- **赛道不同。** torch 的 CPU 性能来自 MKL/oneDNN 的手写 SIMD 微内核；GPU 来自 cuBLAS/cuDNN/flash-attention。
  一个从零写的 Vulkan 后端要在 GEMM/注意力上追平这些，是以"年"计的 kernel 工程投入，且对手在持续前进。
- **"追平"没有终点**，容易陷入无用户可见价值的微优化。

**但窄版本必须做、且高 ROI**：消除**架构性**退化（10x~77x 的那部分）。判据很明确——
把 §1 表格里 `avg_cores ≈ 1` 和 `2.8` 的数字拉到接近物理核数。这**不是**追平 torch，
而是"别比 torch 慢一个数量级"。

### 2.2 ② 疯狂融入新算法

**这是本项目的差异化赛道，也是它已有的强项**（`RLA / RAPT / ZiPT` 已落地，
`development/06-rapt-algorithm.md`、`07-zipt-algorithm.md` 都在）。
新颖架构恰恰是 torch 用户最难的地方（要写自定义 kernel）。

**但"疯狂"在当前引擎上是高风险动作**，三个具体理由：

1. **放大技术债**：`compute_layer_rapt.hpp`(59KB) / `zipt`(52KB) 已经是"大量 eager 算子直调 +
   per-head 循环 + 手工缓存"的风格。照这个风格再加 Mamba-2/GDN/QSA/DSA，
   会把①的串行问题、③的机制并存问题**线性放大**。
2. **回归难查**：**CI 只构建、不跑测试**（见 AGENTS.md 与构建记忆）。在没有自动化测试网的情况下
   快速加算法，等于把正确性押在人工验证上。
3. **已有面还没补齐**：你自己标注"CNN 不完整"。在补完存量之前扩张增量，边际价值递减。

**建议**：把②排在引擎收敛之后，届时加算法的成本会显著下降。

### 2.3 ③ 全面完善引擎设计、简化代码量

**它是①②的使能器，但不能当独立目标。** 现状里的"复杂"是可量化的：

| 遗留/重复 | 规模 |
|---|---|
| 四套表达式求值机制（旧代数 AST / `eval_cpu` / 解释器 / GPU AOT） | 27.6KB 重复 + 两条串行路径（`eval_cpu` 已并行化+向量化，解释器仍串行） |
| 三个引擎实现（CUDA 全链死代码 + 10 处 `#ifdef`） | ~100KB **已于 2026-09-19 清（96a3675）** |
| 49 个接口算子、37 个被层直接调用（含与 DSL 重复的逐元素算子） | 2026-09-19 复核：50 个接口、30 个被层直调 |
| IR-C（`expr_graph.hpp`）已实现但无生产调用方，且 §8.9 证明**当前无处可安全接入** | 22.5KB **已于 2026-09-19 整体删除**（取舍见 `03-ir-optimization.md` §5.3） |

**风险**：③ 最容易变成"大重构 + 无用户可见收益 + 无法定位回归"。
本项目自身就有一个教训：**IR-C 设计很好，但从未接线**——设计完整度不等于价值。

**所以③的正确形态是**：以"修①的瓶颈"为驱动去简化，而不是先简化再找用途。
凡是不服务于①或②的"简化"，一律推迟。

## 3. 建议顺序

> ⚠️ 本节排序基于"性能是目标"的假设。**已确认目标为展示架构能力后，最终排序见 §5.6**（③ 升为主线）。

```
第 1 步（= ③的窄版本 + ①的窄版本：同一件事）
   把 CPU 的 DSL 执行从"串行解释器"变成"并行 lowering"
   → 目标：LayerNorm/Softmax/GeLU 等层的 CPU 核数从 ~1 拉到接近物理核数

第 2 步（= ①的窄版本收尾）
   评估是否还需要 GPU 侧动作；IR-C 已按 §8.9 结论**整体删除**（2026-09-19）

第 3 步（= ②）
   引擎有了统一且不慢的执行面后再扩张算法（Mamba-2 / GDN / QSA / DSA …）

第 4 步（随时可做，低风险）
   清理死代码与无调用点接口（CUDA 全链 ✅ 已清、IR-C ✅ 已删、pool_stats 仍待清）
```

**排序理由一句话**：②是目标，①是约束，③是手段。把手段当成目标会重演 IR-C；
把目标放在约束之前会放大技术债。

## 4. （对照）原排序下的第 1 步：CPU lowering 的具体做法

> 前提改变后，这一步在最终排序里是**第 2 步**（见 §5.6）。内容仍然有效，保留备查。

不改接口、不动 GPU 路径：

1. `eval_cpu`（`expr_dsl.hpp:630-638`）加块并行 + 去掉 per-element `cpu_matrix().span()` 重导出；
2. `eval_expr_impl`（`compute_cpu_engine.hpp:1251`）的广播输出按行块并行、归约改
   per-thread 局部累加器（抄 `col_reduce` 的 `local_acc` 范式，`algebra_matrix.hpp:909-936`）；
   `regs[EXPR_MAX_REGS] = {}` 缩到实际 `num_regs`；
3. 先只覆盖 LayerNorm / RMSNorm / Softmax 三个层，其余不动。

**验证**：用 `build/layer_bench.exe` 的
"进程 CPU 时间 ÷ 墙钟 = 平均核数"指标，看 `--layer layernorm/rmsnorm/softmax` 是否从 ≈1 抬起来；
再对照 `--layer linear/gpt_block` 无回归。不需要 GPU。

**顺带的③收益**：这一步做完，机制 2（`eval_cpu`）与机制 3（解释器）自然合并为
"DSL → lowering"一条路，机制 1（旧代数 AST）的 CPU elementwise 调用面也可随之收敛。

## 5. 已确认前提下的最终建议（目标：展示架构设计能力；主战场：GPU/Vulkan）

### 5.1 这两个前提改变了什么

| 前提 | 影响 |
|------|------|
| 目标是**展示架构设计能力** | **引擎本身的架构就是作品**。于是 ③ 从"手段"升为**主线**；"简化代码量"要改成"**完成并讲清架构**" |
| 主战场是 **GPU/Vulkan** | CPU 性能不是卖点；① 从"约束"降为次要质量项 |
| 不是"追平 torch" | ① 的"追平"目标作废；只保留它作为**架构不一致的证据**这一层意义 |
| 学习/作品集 | **深度 > 广度**：② 从"疯狂加"改成"1–2 个贯穿式展示" |

### 5.2 主线（③）的形态：不是"简化代码量"，而是"完成架构"

评委看的是**一致性、概念数、取舍是否说清**。现状对这三点的欠账：

| 现状 | 对"架构能力"的伤害 |
|------|--------------------|
| **四套求值机制并存** | 第一个问题就是"为什么有四条路？" |
| 三个引擎实现（CUDA 死代码 ~100KB + 10 处 `#ifdef`） | 死代码占比 → 维护判断力存疑 |
| **IR-C 实现了但无生产调用方** | **"设计了却不用"是负分**，比没有更差 |
| 49 个接口算子、37 个被层直调、含与 DSL 重复的逐元素算子 | 边界不清 |
| CPU 同一 IR 退化为串行解释器 | 架构不对称：GPU 是 AOT 融合、CPU 是逐元素解释 |

**目标形态**（§7.3 的三档）：

```
L1 层可见 : dsl::compute / compute_reduce  +  不可约结构原语
L2 内部   : 算子 = DSL 的 lowering 目标（不再对层公开）
L3 后端   : GPU → AOT 融合 shader ;  CPU → 并行 lowering（同一 IR 的第二个后端）
```

这正是 `expr_emitter.hpp` **IR-D 当初的设计意图**："一份 canonical IR → 多后端"。
把 CPU 后端按 **lowering**（而非解释器）补齐，本身就是一个能讲的架构故事，
也顺手把 §1 表格里那个 77x 的架构不一致消掉。

### 5.3 对 IR-C 已做**明确决定**（2026-09-19 执行完毕）

**决定：不接，删干净。** 已删除 `expr_graph.hpp`、`ComputeEngine::begin_expr/end_expr`、
`dsl::start_expr/end_expr`、`FusedChainLayer`、`Tensor::virtual_tag_` 及对应测试/scan 段；
完整取舍见 `03-ir-optimization.md` §5.3、`12-compute-engine-inventory.md` §8.10。

依据（§8.9 实测）：当前层集合里**无处可安全接入**——需要融合的层都以归约为骨架、且都要为
backward 缓存中间量（缓存即图外的第二个消费者）；能融的表达式本就可写成单个 `dsl::compute`。

**重新立项前提**（写进文档才算"说清取舍"）：出现或写出**纯逐元素、同形状、中间量不必为 backward
保留、且长到单个 `dsl::compute` 写不下**的链。届时实现"逃逸检测 + 自动作用域"，而非复活显式录制 API。

### 5.4 ② 的正确尺度：1–2 个**贯穿式**展示算法，不是"疯狂"

作品集里深度 > 广度。挑 1–2 个（如 **Mamba-2** 或 **GDN**），**完整走一遍干净架构**：

```
DSL 表达式 → canonical IR → AOT 融合 shader → 与 compare_with_torch/ 对拍 → 跑通训练
```

这比塞 8 个半成品算法更能证明设计能力。**在引擎收敛之前不要加**——否则新层展示的是混乱，不是能力。

### 5.5 一条被忽视的高价值项：测试与 CI

现状**CI 只构建、不跑测试**。对"展示架构设计能力"而言，**自动化测试是可信度的最佳证据**
（尤其 `gradcheck`、`compare_with_torch/` 对拍、batch>1 的布局测试）。
把已有测试接入 CI：**成本低、可见度高**，优先级应当排进前三。

### 5.6 重排后的四步

| 步 | 动作 | 可展示的产物 |
|----|------|--------------|
| **1** | **架构收敛**：删死代码与重复机制 → 定义 L1/L2/L3 边界 → 对 IR-C 做取舍决定 | 架构图 + 概念数下降 + 死代码清零（CUDA ✅ 96a3675、IR-C ✅ 2026-09-19；余 `pool_stats` 等零调用点接口） |
| **2** | **补齐 CPU 后端为"同一 IR 的 lowering"**（完成 IR-D 的故事） | DSL 在 CPU 不再串行解释；GPU/CPU 对称 |
| **3** | **测试与 CI 落地** | 可自动验证的可信度 |
| **4** | **1–2 个展示型新算法**，走完整架构 | 对拍一致的训练结果 |

**明确不要做**：追平 torch；无差别堆算法；把"减少代码行数"本身当目标（③ 必须有可见产物，否则重演 IR-C）。

### 5.7 仍会改变结论的前提

- 若"展示架构能力"实际指向**特定方向求职/发表**，则第 4 步的算法选择应换成该方向的热点（如 Mamba-2 / 长上下文）。
- 若还想展示 **CPU 侧工程能力**，则第 2 步提前到第 1 步之前。
- 若 GPU 上要展示**性能**（不只是架构），则 §2.1 的"窄版本①"（消除 10x 级退化）需要重新提到主线。
