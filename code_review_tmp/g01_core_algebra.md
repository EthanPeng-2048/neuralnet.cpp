# core+algebra（L0/L1）代码审查

## 模块概览

本组 11 个头文件（约 133KB）：`core_*` 6 个（config/threadpool/errors/file/assert/observer_ptr，L0 硬件与基础设施层）、`algebra_*` 5 个（matrix/expr/ops/compute/span，L1 代数层，含 53KB 核心 `algebra_matrix.hpp`）。`algebra_matrix.hpp` 提供行主序 Matrix（64×64 分块 + 线程池块级并行的 matmul/transpose/broadcast/reduce），`algebra_expr/ops/compute/span` 提供零开销表达式模板 AST 与统一 `compute::apply` 入口。整体质量高：无 throw/try/catch、无 new/delete、无 C 风格转换（core_file 的 reinterpret_cast 是 docs/17 批准的 I/O 边界收敛点）、matmul 各分块 kernel 的索引计算经逐行核对全部正确（含边界尾块）、SIMD 尾部无问题（matmul 按 K 分块且逐元素累加，不存在 cols 非 4 倍数的问题）。主要风险集中在线程池并行路径的确定性（铁律 8）与 L1 用 NN_ASSERT 校验用户输入的尺寸契约。

## 发现

### P1

- **[P1] core_threadpool.hpp:479-521 — parallel_transform_reduce 并行路径与单线程路径逐字节不一致（铁律 8 违反）。** 并行路径各 chunk 以调用者 `init` 为种子独立累加后按 chunk 顺序合并（`partials[c] = local; result = reduce_op(result, p)`）；单线程路径按元素顺序连续累加。浮点加法不满足结合律/交换律：以 `init` 为种子时，chunk 内累加顺序与单线程相同，但"先归并 chunk 部分和再并入"的整体顺序与单线程"逐元素顺序"不同，结果最后位可能不同（例如 3 个 chunk 各 2 元素 [a,b],[c,d],[e,f]：单线程 = (((((0+a)+b)+c)+d)+e)+f，并行 = ((0+((0+a)+b)+c)+d)+... 实际 = ((0+((0+a)+b)+c)+d)+e 与合并顺序 (p0+p1)+p2 结构不同）。代码注释（行 495 "以调用者 init 为单位元"）暗示作者知道非单位元问题但未对齐累加顺序。`nn::transform_reduce`（core_config.hpp:121-126）在 ≥524288 元素时走此并行路径。建议：要么并行路径也按单线程的"逐元素顺序"重排合并（先按全局顺序把各 chunk 的局部结果以固定顺序折入，需保持"init 只在最左"语义——即对 chunk c>0 用"跳过 init 的纯部分和"累加后再与 init 链式结合，实现复杂），要么在该函数注释与调用点明确声明"并行模式逐位结果允许最后位漂移"并评估训练影响，要么把 `Matrix::reduce`/transform_reduce 的大数据路径改为 Kahan 补偿求和使并行/串行同精度。验证方法：构造 1M 元素的随机浮点向量，分别用 `NN_FORCE_SERIAL`（如临时把 PARALLEL_THRESHOLD 调大）与并行跑 `nn::transform_reduce`，逐字节比较。
- **[P1] core_threadpool.hpp:116-164 — wait_for_latch 与 worker 线程对 tasks_/queue_mutex_ 的访问存在潜在唤醒丢失（lost wakeup）风险。** worker 在 `condition_.wait(lock, pred)` 中等待 `stop_ || !tasks_.empty()`；`wait_for_latch` 的 cv 等待用 `condition_.wait_for(lock, 100μs, latch==0)`。竞态窗口：调用线程刚把任务入队（`tasks_.emplace` 后 `notify_all`），但 worker 恰好在 `stop_.load()==false && tasks_.empty()` 为真时即将进入 wait——`wait` 的谓词在锁内重读，此路径安全。真正的隐患在 `stop_` 与 latch 的交互：析构设 `stop_=true; notify_all`，但若某次 `parallel_for_*` 的 `wait_for_latch` 仍在自旋（100μs cv 超时循环），而 worker 在 stop 后退出（不再消费剩余 chunk 任务）——此时调用线程的 latch 永远不归零（因为 worker 已退出、未执行 fetch_sub），**调用线程将自旋于 100μs 循环里永久卡死**。触发条件：ThreadPool 析构（static 全局池在进程退出时）与进行中的并行调用重叠。`global_thread_pool()` 是 function-local static，析构发生在 main 返回后；若某线程池并行调用尚未完成（如 atexit/静态析构期间），会死锁。建议：析构前显式 `stop_ + 等待队列清空`，或文档化"进程退出前必须完成所有并行调用"；更稳妥的是析构时若 `tasks_` 非空则继续消费完再退出（`stop_` 只表示不再接受新任务）。
- **[P1] core_threadpool.hpp:74-91 — submit() 死代码 + 违反"批量入队"设计原则。** 全库 grep 无调用方（仅本文件定义），且每次调用都 `make_shared<packaged_task>` + `std::bind`，与本文件头部注释"消除每分块一次 shared_ptr 堆分配"的设计目标相悖。属 D 维度死代码（-Wall -Werror 下未使用私有方法可能触发 -Wunused-private-field 警告，但 Clang 对此警告较弱）。建议：删除或改为 `[[nodiscard]]` + 文档标注"非性能敏感路径专用"。
- **[P1] algebra_matrix.hpp:87-93 — Matrix::span() 返回指向 data_ 的 span，但 Matrix 允许 `resize()` 触发 vector 重分配，任何持有旧 span 的代码在 resize 后全部悬垂。** `resize`（行 79-85）直接 `data_.resize(rows*cols)`，若容量不足则 vector 内部 realloc，此前通过 `span()`/`at()`/`set_value()` 拿到的 `std::span<Scalar>`/裸指针全部失效。`multiply_to`/`transpose_to` 等热路径在拿到 `span()` 后立即使用（中间无 resize），安全；但上层（L2 计算层）若跨调用持有 Matrix 的 span 再调用 `resize`/`operator=` 即 use-after-free。属 B 维度生命周期风险，本文件内部无违规，但 API 层面缺保护（如 resize 前断言无 span 在途不可行，需文档化）。建议：在 `span()`/`resize` 注释中明确"span 生命周期限于到下一次 resize/operator= 之前"，或在 resize 中加 `NN_ASSERT(data_.capacity() >= rows*cols || "caller must not hold spans")` 之类的防御（实际不可检测，纯文档）。
- **[P1] algebra_matrix.hpp:53-59 — require_same_shape 用 NN_ASSERT 校验用户输入尺寸，Release(NDEBUG) 下完全失效，OOB 读/写无保护。** `add_inplace`/`broadcast_row_inplace`/`broadcast_col_inplace` 的尺寸检查都走 `NN_ASSERT`（core_assert.hpp:12-13，NDEBUG 时展开为 `(void)0`）。L1 层头注释（行 35-38）明确"L1 用 NN_ASSERT 做编程错误检查"，但 L2 计算层（如 LayerNorm 调用 broadcast_row_inplace）传入的是**用户构建的矩阵**，维度错误是运行时用户输入错误而非"编程错误"，Release 下直接 OOB 读写（`add_inplace` 行 784-786 的 `nn::transform` 对越界数据直接读写）。这违反铁律 1 的精神（"错误走 Result<T>"）：用户输入类校验应在 L2 用 Result，L1 的 NN_ASSERT 只该用于内部不变量（如 `&result != this`）。建议：要么在 L2 调用点补 Result 校验（需逐个调用点审计），要么 L1 对"跨矩阵维度匹配"这类**用户输入边界**改为返回 bool/Result 而非 abort。验证方法：`-DNN_DEBUG=1`（即非 NDEBUG）构建 + 构造维度不匹配的 add_inplace 调用，确认 Release 构建（-DNDEBUG）下无 abort 且后续读到越界数据。
- **[P1] algebra_matrix.hpp:50 — index(row, col) = row * cols_ + col 在 size_t 上对超大矩阵可能溢出（row*cols_ 超出 2^64-1）。** 64 位平台 `size_t` 上限 2^64，实际矩阵 rows*cols 若超过 2^64（≈1.8e19 元素，18 EB）不现实，但 `row * cols_ + col` 的**中间** `row * cols_` 在 row、cols 都接近 2^32 时（4G×4G）才溢出，实际内存分配（`data_(rows*cols)` 行 64-65）会先抛 bad_alloc/返回 unexpected，所以**实际不可达**，仅理论 UB。标 P1 是因铁律 A 维度"int 溢出"要求核对：`data_(rows * cols)` 本身的 `rows*cols` 乘法在构造期也会先于 vector 分配溢出。建议：在构造/resize 中加 `NN_ASSERT(rows <= SIZE_MAX / max(cols,1))` 防乘法溢出（防御性）。

### P2

- **[P2] core_config.hpp:69/85/102/144 — nn::for_each/transform 用 `std::ranges::distance(first, last)` 计算长度，要求迭代器满足 std::sized_sentinel_for，对非随机访问迭代器（如 std::list::iterator）编译失败。** 本库内所有调用点传入的都是 `span::iterator`（随机访问）或 `views::iota` 迭代器，实际安全；但 API 注释（行 62 "用法与 std::for_each 完全一致"）误导上层以为可传任意迭代器。建议：注释改为"要求随机访问迭代器（用于距离计算）"，或加 `std::random_access_iterator` 约束。
- **[P2] core_threadpool.hpp:172/235/338/398/463/530 — parallel_for_each 等用 `std::ranges::distance` 对 `views::iota` 迭代器调用是合法的（iota 是 sized），但 `parallel_for_each` 接收的迭代器类型由模板推导，调用点传 `block_indices.begin()/end()`（std::views::iota_view 的 iterator）也合法。无实际 bug，仅 P3 级 API 一致性：`nn::for_each`（core_config.hpp:67）要求随机访问，但 `parallel_for_each`（threadpool:170）未显式约束，两者 API 面不一致。建议：统一加 `std::random_access_iterator` 约束。
- **[P2] core_threadpool.hpp:116-117 — wait_for_latch 自旋阶段无 `std::atomic_thread_fence` 隔离，`latch.load(acquire)` 在 16 次自旋中反复读同一原子变量，对弱内存序平台（ARM）可能读到 stale 值导致自旋偏长，但功能正确（最终进入 cv 等待）。仅性能微优化，非 bug。建议：自旋循环加 `std::atomic_signal_fence(std::memory_order_acquire)` 提示。
- **[P2] algebra_matrix.hpp:200/259/319/323/388/429/490/531/644/650/705/746 — `std::array<Scalar, BLOCK_SIZE * BLOCK_SIZE> b_block{}` 在 lambda 栈上分配 16KB×2=32KB（transpose_multiply 路径），与 core_config.hpp:36-37 的"b_block 栈预算 64KB"一致（64×64×4=16KB/块）。无 bug，但 `std::array` 值初始化 `{}` 每次都 memset 16KB（即使只用部分），在热路径是 16KB 的冗余清零。建议：改为 `std::array<Scalar, BLOCK_SIZE * BLOCK_SIZE> b_block;`（不初始化）+ 仅写入实际使用的 `k_len*j_len` 元素（当前代码已经只写 `jj<j_len, kk<k_len` 范围，但读取也只读该范围，所以可安全去初始化——需确认 subspan 读取不越出）。
- **[P2] core_errors.hpp:26-30 — check_result 包装器提供 [[nodiscard]] 但全库 grep 无调用点（疑似死代码）。** 设计意图是"让丢弃 Result 的调用在编译期告警"，但 `Result<T>` 本身是 `std::expected` 别名，无法直接加 nodiscard，check_result 是替代方案。若全库无调用点，说明实际错误传播靠**调用方手动 `if (!r) return ...`**，缺少编译期强制。建议：要么在关键公共 API（load_text_file 已加 nodiscard，但 parse_number 的 Result 别名无 nodiscard）补 `[[nodiscard]]`，要么删除 check_result。
- **[P2] core_file.hpp:48-85 — write_pod/read_pod 返回 bool 而非 Result，调用方若忘记检查即静默失败。** 头注释（行 43）明确"返回值：流的 good 状态（false = 读/写失败，调用方决定错误语义）"，但 `read_pod` 对**部分读**（stream 在 `size_bytes` 中途 EOF）也返回 false（`is` 状态变 bad），调用方无法区分"全失败"与"部分读"。对序列化（model_serialization.hpp 调用 read_pod 读 v4 头）而言，部分读会导致后续字段解析错乱。建议：read_pod 返回 `Result<std::size_t>`（实际读取字节数）或至少 `Result<void>`，让调用方明确处理。
- **[P2] algebra_expr.hpp:43 — Val::eval 标记 `constexpr`，但 ops::Exp/Log/Sqrt 等（algebra_ops.hpp:63/69/75）的 apply 非 constexpr（std::exp 等运行时函数）。** 表达式树中混有 constexpr 叶节点与非 constexpr 算子节点，`constexpr` 标注在 `UnaryExpr::eval`（行 55）上是**虚假的**——`constexpr auto eval` 要求函数体在常量求值下可求值，但 `ops::Exp::apply` 调 `std::exp`（非 constexpr），整条链无法用于 constexpr 上下文。`UnaryExpr::eval` 的 `constexpr` 是**可调用**（非 constexpr 函数调用在 constexpr 函数中允许，只要不在常量表达式中实际求值），所以编译通过，但**误导**上层以为可用 constexpr 上下文。建议：去掉 `UnaryExpr::eval`/`BinaryExpr::eval`/`TernaryExpr::eval` 的 `constexpr`（保留在 Val::eval 即可），或文档说明"constexpr 仅指函数签名，实际求值需运行时"。
- **[P2] algebra_span.hpp:54-57 — Span::subspan(offset, count) 无边界检查，offset+count > size_ 时返回越界 Span，后续 operator[] 是 OOB 读。** ConstSpan::subspan 同（行 118-121）。调用点（如 compute_cpu_engine.hpp 的切片操作）依赖上层保证合法。建议：加 `NN_ASSERT(offset <= size_ && count <= size_ - offset)`（与 Matrix::at 风格一致，Release 零开销）。
- **[P2] core_observer_ptr.hpp:56-61 — operator== 对 observer_ptr 与 observer_ptr 用 = default，但 observer_ptr 是类模板，= default 在 C++20 之前需要所有成员可比较；C++26 下 OK。但 `operator==(const observer_ptr& p, std::nullptr_t)`（行 57）与 `operator==(const observer_ptr&, const observer_ptr&)`（行 56）构成重载集，`p == nullptr` 走行 57（显式），`p == other` 走行 56，正确。无 bug，仅 P3 级：`make_observer(T&)` 与 `make_observer(T*)` 重载在 T 为指针类型时（如 `observer_ptr<int*>`）会歧义——`make_observer<int*>(ptr_to_int)` 中 T=int*，`T& = int*&` 与 `T* = int**` 不歧义（后者需传 int**），实际安全。
- **[P2] core_threadpool.hpp:97-105 — chunk_count 用 `workers_.size()` 计算分块数，但 `workers_` 在构造后不变，而 `global_thread_pool()` 是单例，多进程/多实例场景下 workers 数固定。无 bug，但 `total / MIN_CHUNK` 在 total 极大（>2^31）时 `nw`（size_t）与 `total/MIN_CHUNK`（size_t）的 min 正确，无溢出。

- **[P3] algebra_compute.hpp:38 — compute::apply 的 `nn::for_each(indices.begin(), indices.end(), ...)` 对 n >= 524288 触发并行，但并行路径中 `x[i] = expr.eval(i)` 是**独立元素读写**（无数据依赖），确定性安全。无 bug，仅建议：对 n < 阈值但 >= 4096 的场景考虑 SIMD 手动展开（当前 nn::for_each 串行路径是普通 for 循环，依赖编译器向量化，但 lambda 中的 `expr.eval(i)` 调用链可能阻碍自动向量化——建议对常见表达式（纯 Val/UnaryExpr）特化出 SIMD 循环）。

## 已知问题核对

- **col_reduce 并行非逐字节一致（AGENTS.md §12"未修"项）**：**仍存在**。证据：`algebra_matrix.hpp:843-936` `col_reduce` 的并行路径（行 896-934）用 `n_threads = hardware_concurrency()` 组本地累加器 `local_acc[n_threads*C]`（行 898），各线程对**行块**（`r0..r_end`，行 910-911）独立累加到 `local_acc[t*C+c]`，归并阶段（行 927-934）按 `t=0,1,...,n_threads-1` 顺序把 `local_acc[t*C+c]` 折入 `out[c]`。单线程路径（行 879-894）按 `r=0..R-1` 行顺序、`c=0..C-1` 列顺序累加到 `out[c]`。**累加顺序不同**：单线程是 `out[c] = reduce_op(out[c], v[r][c])` 逐行；并行是 `out[c] = local_acc[0*C+c]` 然后 `reduce_op(out[c], local_acc[t*C+c])`（t=1..n_threads-1），其中 `local_acc[t*C+c]` 是第 t 组行块内所有 `v[r][c]` 的**内部链式**累加。浮点加法不结合，结果最后位与单线程不同。代码注释（行 925-926）声称"reduce_op 满足结合律，结果与单线程一致"——**该注释对浮点加法不成立**（结合律是数学语义，不是 IEEE 754 逐位语义）。AGENTS.md §12 将其列为"未修"，核实仍存在于当前代码。建议：要么改为 Kahan 补偿求和（并行/串行同精度），要么把注释改为"并行模式逐位结果允许最后位漂移，训练场景影响可忽略"并补测试覆盖。

## 其他观察

- **algebra_matrix.hpp 无 CPU/GPU 零拷贝 reshape 相关逻辑**：本文件（L1）只有 `Matrix`（CPU 存储）与 `span()` 视图；GPU 零拷贝语义（docs/08 坑 6"CPU 分支 reshape 需复制数据，GPU 保持零拷贝"）在 `compute_gpu_tensor_impl.hpp`/`compute_tensor.hpp`（L2，非本组文件）中实现，本组无相关代码，无需核对。
